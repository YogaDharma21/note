Go Backend Codebase Analysis

Target Audience: Express.js Developer transitioning to Go (using Fiber)

1. Project Structure Overview

This Go backend follows a Clean Architecture / Layered Architecture pattern, very similar to how you would structure an Express app, but with stricter separation enforced by Go's visibility rules.

cmd/ internal/ pkg/

Folder Breakdown

  • cmd/rest/ -> Entry point (like your app.js or server.js)
  • internal/ -> Private application code (cannot be imported by other modules)
    • controller/ -> Route handlers (like Express route files)
    • service/ -> Business logic (like Express service layers)
    • repository/ -> Data access (like Express models/repositories)
    • entity/ -> Database models (like Sequelize/TypeORM entities)
    • dto/ -> Request/Response shapes (like TypeScript interfaces)
    • pkg/serverutils/ -> Shared utilities (middleware, validators)
  • pkg/ -> Public reusable packages (database connection)

2. Entry Point: cmd/rest/main.go

This is where everything wires together. In Express, you might have:

// Express equivalent (app.js)
require('dotenv').config();
const app = express();
app.use(express.json({ limit: '10mb' }));
app.use(errorHandler);

const db = require('./config/database');

const exampleRepo = new ExampleRepository(db);
const exampleService = new ExampleService(exampleRepo);
const exampleController = new ExampleController(exampleService);

app.use('/api', exampleController.router);

In Go with Fiber, the same logic lives in main.go:

func main() {
    godotenv.Load()
    app := fiber.New(fiber.Config{
        BodyLimit: 10 * 1024 * 1024,
    })

    app.Use(serverutils.ErrorHandlerMiddleware())

    db := database.ConnectDB(os.Getenv("DB_CONNECTION_STRING"))

    // Dependency Injection - manually wired here
    exampleRepository := repository.NewExampleRepository(db)
    exampleService := service.NewExampleService(exampleRepository)
    exampleController := controller.NewExampleController(exampleService)

    api := app.Group("/api")
    exampleController.RegisterRoutes(api)
}

3. The Example Feature: Hello World

Let's trace a request through all layers using the Hello World endpoint.

3.1 DTO (Data Transfer Object)

DTOs define the shape of incoming/outgoing JSON. In Express/TypeScript, you'd use interfaces or Zod schemas:

// Express + TypeScript equivalent
interface HelloWorldRequest {
  name: string;
}
interface HelloWorldResponse {
  message: string;
}

In Go, DTOs are structs with json tags and validate tags:

// internal/dto/example_dto.go
type HelloWorldRequest struct {
    Name string `json:"name" validate:"required,min=3"`
}

type HelloWorldResponse struct {
    Message string `json:"message"`
}

3.2 Entity (Database Model)

Entities represent your database tables. In Express, this might be a TypeORM entity:

// Express + TypeORM equivalent
@Entity()
class Example {
  @Column()
  message: string;
}

In Go, entities are plain structs (no class, no decorators):

// internal/entity/example_entity.go
type Example struct {
    Message string `json:"message"`
}

3.3 Controller (Route Handler)

Controllers handle HTTP concerns. In Express, routes are usually in separate files or a router:

// Express equivalent (example.routes.js)
router.post('/hello-world', async (req, res, next) => {
  try {
    const result = await exampleService.helloWorld(req.body);
    res.json({ success: true, data: result });
  } catch (err) {
    next(err);
  }
});

In Go with Fiber:

// internal/controller/example_controller.go
func (c *exampleController) HelloWorld(ctx *fiber.Ctx) error {
    var req dto.HelloWorldRequest
    if err := ctx.BodyParser(&req); err != nil {
        return err
    }

    err := serverutils.ValidateRequest(req)
    if err != nil {
        return err
    }

    res, err := c.service.HelloWorld(ctx.Context(), &req)
    if err != nil {
        return err
    }

    return ctx.JSON(serverutils.SuccessResponse("Success", res))
}

Go vs Express Controller Comparison

Aspect Express.js Go + Fiber
Parse Body req.body (auto-parsed by middleware) ctx.BodyParser(&req) (explicit)
Validation const { error } = schema.validate(req.body) serverutils.ValidateRequest(req) (struct tags)
Pass Context req object carries context implicitly ctx.Context() extracts Go context for services
Return JSON res.json(data) ctx.JSON(data)
Error Handling try/catch + next(err) return error (middleware catches it)

3.4 Service (Business Logic)

Services contain business logic independent of HTTP. In Express, services are just plain classes:

// Express equivalent
class ExampleService {
  constructor(repository) {
    this.repository = repository;
  }

  async helloWorld(req) {
    await this.repository.ping();
    return { message: `Hello ${req.name}` };
  }
}

In Go, services are structs implementing interfaces:

// internal/service/example_service.go
type IExampleService interface {
    HelloWorld(ctx context.Context, req *dto.HelloWorldRequest) (*dto.HelloWorldResponse, error)
}

type exampleService struct {
    exampleRepository repository.IExampleRepository
}

func (c *exampleService) HelloWorld(ctx context.Context, req *dto.HelloWorldRequest) (*dto.HelloWorldResponse, error) {
    _, err := c.exampleRepository.Ping(ctx)
    if err != nil {
        return nil, err
    }

    return &dto.HelloWorldResponse{
        Message: fmt.Sprintf(`Hello %s`, req.Name),
    }, nil
}

Critical Go Concepts for Express Devs

Context: Every request gets a context.Context that carries deadlines, cancellation signals, and values across API boundaries. In Express, the req object does this implicitly. In Go, you must explicitly pass ctx to database calls and services.

Error Returns: Go has no exceptions (except panics). Functions return (value, error). You must check errors. No try/catch blocks.

Pointers: *dto.HelloWorldRequest is a pointer. Go passes structs by value (copy) by default. Pointers avoid copying large structs and allow mutation.

3.5 Repository (Data Access)

Repositories handle raw SQL. In Express with raw queries:

// Express + pg equivalent
class ExampleRepository {
  async ping() {
    const result = await db.query('SELECT $1 AS message', ['hello']);
    return result.rows[0];
  }
}

In Go with pgx (PostgreSQL driver):

// internal/repository/example_repository.go
func (n *exampleRepository) Ping(ctx context.Context) (*entity.Example, error) {
    row := n.db.QueryRow(ctx, `SELECT 'hello' AS "message"`)
    var example entity.Example
    err := row.Scan(&example.Message)
    if err != nil {
        return nil, err
    }
    return &example, nil
}

Go vs Express Repository Comparison

Aspect Express + pg Go + pgx
Query Execution db.query('SELECT ...', [params]) db.QueryRow(ctx, 'SELECT ...', params)
Reading Results result.rows[0] row.Scan(&variable)
SQL Injection Safety Parameterized queries $1, $2 Parameterized queries $1, $2
Transactions await db.query('BEGIN') UsingTx() returns new repo bound to transaction

4. Database Layer

Connection

// pkg/database/connection.go
func ConnectDB(connectionString string) *pgxpool.Pool {
    db, err := pgxpool.New(context.Background(), connectionString)
    if err != nil {
        log.Panicf("Unable to connect to DB: %v", err)
    }
    err = db.Ping(context.Background())
    if err != nil {
        log.Panicf("Failed to ping: %v", err)
    }
    return db
}

This returns a connection pool. In Express, you might use a singleton or dependency injection container.

Queryer Interface

// pkg/database/queryer.go
type DatabaseQueryer interface {
    Exec(ctx context.Context, sql string, arguments ...any) (pgconn.CommandTag, error)
    Query(ctx context.Context, sql string, args ...any) (pgx.Rows, error)
    QueryRow(ctx context.Context, sql string, args ...any) pgx.Row
}

This is an abstraction. Both *pgxpool.Pool and *pgx.Tx (transactions) implement this interface, allowing repositories to work with either without changes.

5. Error Handling & Middleware

Global Error Handler

// internal/pkg/serverutils/error_middleware.go
func ErrorHandlerMiddleware() fiber.Handler {
    return func(c *fiber.Ctx) error {
        defer func() {
            if r := recover(); r != nil {
                log.Printf("[PANIC RECOVERED] %v\n%s", r, debug.Stack())
                _ = c.Status(fiber.StatusInternalServerError).JSON(fiber.Map{
                    "error": "Internal Server Error",
                    "message": fmt.Sprintf("%v", r),
                })
            }
        }()

        err := c.Next()
        if err == nil { return nil }

        if fiberErr, ok := err.(*fiber.Error); ok {
            return c.Status(fiberErr.Code).JSON(ErrorResponse(fiberErr.Code, fiberErr.Message))
        }

        if ve, ok := err.(*ValidationError); ok {
            return c.Status(fiber.StatusBadRequest).JSON(ValidationErrorResponse(ve.ToErrorDetails()))
        }

        log.Printf("[ERROR] %v", err)
        return c.Status(fiber.StatusInternalServerError).JSON(ErrorResponse(
            fiber.StatusInternalServerError, err.Error(),
        ))
    }
}

This replaces Express's app.use((err, req, res, next) => { ... }) error handler plus panic recovery.

Validation

Uses go-playground/validator with struct tags (similar to Zod/Joi):

// DTO
type HelloWorldRequest struct {
    Name string `json:"name" validate:"required,min=3"`
}

// Validator
func ValidateRequest(req any) error {
    err := validate.Struct(req)
    if err == nil { return nil }

    var details []ValidationErrorDetail
    for _, err := range err.(validator.ValidationErrors) {
        details = append(details, ValidationErrorDetail{
            Field:   err.Field(),
            Message: err.Tag(),
        })
    }
    return NewValidationError(details)
}

6. Notebook Feature: A More Complete Example

The Notebook feature shows a CRUD-like flow with proper entity-to-DTO mapping.

Request Flow

POST /api/notebook/v1
Body: { "name": "My Notebook", "parent_id": "uuid-here" }

1. Controller: Parse JSON -> Validate
2. Service: Map DTO -> Entity (add Id, timestamps)
3. Repository: INSERT INTO notebook (...)
4. Service: Return response DTO
5. Controller: Wrap in BaseResponse -> JSON

Service Mapping (DTO -> Entity)

func (c *notebookService) Create(ctx context.Context, req *dto.CreateNotebookRequest) (*dto.CreateNotebookResponse, error) {
    notebook := entity.Notebook{
        Id:        uuid.New(),
        Name:      req.Name,
        ParentId:  req.ParentId,
        CreatedAt: time.Now(),
    }

    err := c.notebookRepository.Create(ctx, &notebook)
    if err != nil {
        return nil, err
    }

    return &dto.CreateNotebookResponse{
        Id: notebook.Id,
    }, nil
}

7. Go vs Express: Architecture Summary

Pattern Express.js Go + Fiber
Type System TypeScript (optional, compile-time only) Native static typing, enforced at compile time
Interface Usage Rarely used (duck typing) Pervasive (every layer has I<Name> interface)
Dependency Injection Manual or container (Awilix, TSyringe) Manual constructor injection (always explicit)
Error Handling try/catch + error middleware return (value, error) - no exceptions
Validation Zod, Joi, express-validator Struct tags + go-playground/validator
Concurrency Single-threaded event loop Goroutines (lightweight threads)
Memory Garbage collected, higher overhead Garbage collected, much lower overhead
ORM/Query Builder Sequelize, Prisma, TypeORM Raw SQL with pgx (type-safe)

8. Key Takeaways for Express Developers

  1. No Classes, Just Structs: Go uses struct for data, not classes. Methods are attached to types, but there is no inheritance.
  2. Interfaces Are Explicit: Every major component declares an interface (IExampleService). This makes testing trivial - just mock the interface.
  3. Error Returns, Not Exceptions: Go has no exceptions (except panics). Functions return (result, error). You check if err != nil. No try/catch blocks.
  4. Context Propagation: context.Context is passed down the call stack for cancellation, timeouts, and tracing.
  5. Zero Runtime Reflection: JSON tags and validate tags are read at runtime, but the struct shapes are fully known at compile time.
  6. Fiber Feels Like Express: The API is intentionally similar: app.Use, ctx.JSON, ctx.BodyParser, route groups.
Summary: This codebase is a well-structured Go backend using Fiber. The architecture mirrors Express patterns (controllers, services, repositories) but enforces stricter typing, explicit error handling, and compile-time safety. If you know Express, you already understand the architecture - you are just learning Go's syntax and idioms.
